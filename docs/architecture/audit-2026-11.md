## Findings, by severity

### 1. High — deck writes can tear, and nothing has a version

No Prisma model has a `version` column. `Deck` has `updatedAt` and an `idempotencyKey` for
create retries. It has no token a later update can check.

These handlers write two or more statements with the global `prisma` client and no
`$transaction`:

| Write                                                                                    | Where                                                        | What can be left behind                                                                                  |
| ---------------------------------------------------------------------------------------- | ------------------------------------------------------------ | -------------------------------------------------------------------------------------------------------- |
| Add one card, then touch `deck.updatedAt`                                                | `src/app/api/decks/[id]/cards/route.ts` lines 110–114        | A card row whose deck timestamp did not move.                                                            |
| Delete every card, then touch `deck.updatedAt`                                           | same file, lines 233–237                                     | Cards gone, timestamp unchanged.                                                                         |
| Delete one card, then touch `deck.updatedAt`                                             | `src/app/api/decks/[id]/cards/[cardId]/route.ts` lines 26–30 | Same.                                                                                                    |
| Update one card, then touch `deck.updatedAt`                                             | same file, lines 72–80                                       | The row changed, the deck timestamp did not.                                                             |
| Merge a printing by adding the quantities read a moment earlier, then delete the old row | `src/app/api/collection/[id]/route.ts` lines 56–64           | Lost increments under two concurrent edits, or a merged row whose source row still exists.               |
| Increment a collection row by `existing.quantity + quantity` after `findUnique`          | `src/app/api/collection/route.ts` lines 98–104               | Lost increments. The unique constraint only covers the insert race, which the handler already documents. |

The bulk edit is the counter-example, and it is the pattern to generalise.
`applyDeckCardChanges` takes a transaction client; `PATCH` runs it inside
`prisma.$transaction` (`cards/route.ts` lines 146–209) and returns 409 on
`StaleDeckCardsError` when a deleted or resized row is no longer there. That check is a
row count, not a version: two editors changing different cards both succeed, and the
second command-zone write wins silently.

Two multi-statement writes are deliberate and documented as single statements so a
concurrent caller re-checks a condition: `claimAllowanceUnit`
(`src/lib/ai/usage/ledger.ts` lines 37–44) and `fileReport`
(`src/app/api/community/decks/[id]/reports/route.ts`). `recordEdhrecSnapshot` upserts and
then deletes old rows (`src/lib/meta/snapshots.ts` lines 72–81) and swallows the error,
because a failed snapshot must not fail the meta response. Those three should stay
single statements; they are not the deck aggregate.

There are **7** `$transaction` call sites in production and **33** models.

### 5. High — the persistent deck can represent states the rules forbid

`DeckCard` in `prisma/schema.prisma` (lines 277–302) stores `isCommander` and `isPartner`
as independent booleans next to `zone`, `category` and `quantity`. `format`, `zone`,
`pairingType` and `category` are `String`. The schema has **0** enums.

The TypeScript `Deck` (`src/lib/deck/types.ts` lines 69–96) is a step further and still
anemic: `commander`, `partner` and `companion` are independent nullables beside
`pairingType`, so a partner with no commander type-checks. `maybeboard` is a second list
mirrored from `zone === "maybeboard"`. `DeckCard.id` is a `string` that is a database id
after a save and a Scryfall id before it (`makeDeckCard` in
`src/lib/deck/store-card-faces.ts`). `DeckStats` on the same type imports
`commander-rules-check`, `themes`, `format-stats`, `mana-alignment` and `turn-one`, which
import `types.ts` back.

The behaviour that should sit on those types lives elsewhere: pairing in the store,
validation in `src/lib/deck/validation.ts`, colour identity in both `validation.ts` and
`color-identity.ts`.

### 8. Medium — the colour-identity rule is written twice, and a second Game Changer definition is dead

An exact-body comparison of production functions of at least 12 code lines and 180
normalised characters found **0** cross-file clones. The duplication that matters is a
rule written twice, plus an exported heuristic nothing in production calls.

Colour identity. `src/lib/deck/validation.ts` does not import `color-identity.ts`. It
has its own predicate twice: `checkCardColorIdentity` (lines 25–35) and
`checkColorIdentityViolations` (lines 133–141). Both build a set from the commander and
the partner and look for a colour outside it. `getColorIdentityViolations` and
`isCardOutsideColorIdentity` in `src/lib/deck/color-identity.ts` (lines 12–35) do the
same job for stats, the editor and generated-deck legality. A change to the rule is a
two-file edit. The exported `checkColorIdentity` (validation.ts lines 227–232) has no
production caller; only `validation.test.ts` calls it.

Game Changers. `detectGameChanger` (validation.ts lines 235–243) treats oracle text
containing "take an extra turn" or "win the game" as a Game Changer. Nothing in
production calls it; only `validation.test.ts` does. The live check is
`checkGameChangers` (lines 144–148), which reads the card's `isGameChanger` flag. The
heuristic is a second definition of the term, waiting for the next importer.

## Quick wins

Each of these is one pull request. None of them is "split `store.ts`".

1. **Move `src/app/api/ai/build/types.ts` into `src/lib/ai/`.** Behaviour-preserving.
   Removes the 4 `lib → app` edges and the 3 `ui/hooks → app` edges that point at it
   (7 of the 21 baseline entries). Existing AI tests are the characterisation.
2. **Move `DeckStats` and the analysis result types out of `src/lib/deck/types.ts`.**
   `types.ts` imports the analysis modules that import `types.ts` back. Moving the report
   type removes that cycle. It does not remove `turn-one.ts` importing
   `OPENING_HAND_SIZE` from the playtest engine, or the import and meta cycles. The
   codemod rewrites every importer in the same PR.
3. **Render tests for the 0% screens that contain rules**, starting with
   `DeckEditor.tsx` (0/238 statements, cyclomatic 23) and the builder page (0/1,202).
   Tests only. The deck store is already at 97.8% and does not need a new suite before
   a move; it needs the existing `store-*.test.ts` files kept green.
4. **A fix PR, not a refactor, for the collection quantity lost update.** One conditional
   increment, with a Red test that two concurrent adds both stick. Separate from the
   architectural series because it changes behaviour.
5. **A fix PR that wraps the four deck-card-plus-`updatedAt` pairs in `$transaction`.**
   Red test: the deck timestamp moves only when the card write commits. The version
   column is the later step, not this one.

Leaving the four info-level orphans is an owner decision (ADR 0007, orphans are advisory).
This audit does not recommend deleting them inside a structural PR.
